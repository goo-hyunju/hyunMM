hyunMM이란

hyunMM은 AI DAW다. "AI가 음악을 만들어주는 프로그램"이 아니라, 사람이 DAW처럼 음악을 조작하면 AI가 그 작업 맥락을 이해하고 함께 편곡·생성하는 데스크톱 앱이다. CLAUDE.md · docs/planning/product-plan.md

  • 사용자가 주체다. 드럼패드·가상 키보드·타임라인·믹서로 직접 음악을 만든다. DAW가 본체다.
  • AI는 협업자다. 현재 프로젝트 상태(트랙·클립·BPM·키)를 컨텍스트로 받아 "여기에 어울리는 베이스라인" 같은 요청을 처리한다. 실제로 모든 생성 요청에는 프로젝트 컨텍스트 스냅샷이 필수로 포함된다. service/app/api/schemas.py:120-125
  • AI 출력은 완성곡이 아니라 클립이다. 오디오 스템(WAV) 또는 MIDI 클립으로 타임라인에 올라가고, 수락·수정·삭제는 사용자가 한다. 클립에는 출처(origin.source: 'user' | 'ai')가 기록된다. renderer/src/app/types/project.ts:42-46

전체 아키텍처

프로세스 3개가 협력한다: Electron main(관리자) · Renderer(DAW 본체) · Python FastAPI 서비스(AI). 저장은 DB 없이 로컬 프로젝트 파일이다.

기동 시퀀스

npm run dev 하나로 전체가 뜬다. electron-vite가 main/preload/renderer를 빌드·기동하고, main의 app.whenReady()에서 Python 서비스 spawn과 창 생성이 일어난다. app/main/index.ts:48-55

  1. npm run dev → electron-vite가 main·preload·renderer를 동시 기동한다. package.json scripts.dev
  2. Electron main이 service/.venv/Scripts/uvicorn.exe(win32 기준)를 spawn — 인자 app.main:app --port 8930, cwd는 service/. app/main/index.ts:13-21
  3. 동시에 BrowserWindow 생성. dev에서는 ELECTRON_RENDERER_URL(vite dev 서버), 배포 빌드에서는 out/renderer/index.html을 로드한다. app/main/index.ts:41-45
  4. 렌더러는 preload가 노출한 window.hyunmm.serviceUrl(http://127.0.0.1:8930)로 서비스에 접근한다. 없으면 fallback 상수 사용. renderer/src/app/serviceClient.ts:3-7
  5. 종료: before-quit에서 serviceProcess.kill(). app/main/index.ts:61-64
패키징 미비 spawn 경로는 개발 단계 전제(service/.venv 직접 실행)다. 배포 패키징 시 번들된 Python 런타임 경로로 교체 예정이라는 주석이 코드에 명시돼 있다. app/main/index.ts:11-12 배포용 패키저(electron-builder 등)는 아직 없다.

서비스 없이도 동작 (graceful degradation)

spawn이 실패해도 앱은 죽지 않는다. serviceProcess.on('error')에서 로그만 남기고 null 처리 — 서비스가 없어도 DAW 본체는 동작하고 AI 기능만 비활성이 되는 설계다. app/main/index.ts:23-27

단일 시계 원칙

유일한 시계는 AudioContext.currentTime이다. Date.now()나 performance.now()가 아니라 오디오 하드웨어 클럭을 쓴다 — 소리와 화면이 같은 시계를 봐야 어긋나지 않는다. transport의 전체 상태는 anchor 쌍 (ctxTime, beats) + bpm 뿐이다. renderer/src/audio-engine/transportMath.ts:1-2

  • AudioContext는 앱 전체에 싱글턴 1개. latencyHint: 'interactive'. audioContext.ts:4-9
  • transport도 모듈 싱글턴 — 모듈 스코프 원시값만 사용, zustand를 모른다. transport.ts:1-15
  • 시간 계산은 순수 함수로 분리되어 vitest 테스트 대상이다. transportMath.ts · transportMath.test.ts

anchor 수학 — 위치는 저장하지 않고 계산한다

재생 위치를 매 틱 저장·갱신하지 않는다. "ctx 시간 T일 때 위치가 B beat였다"는 기준점(anchor) 하나만 기억하면, 현재 위치는 언제든 1차식으로 계산된다.

함수역할근거
positionBeatsAt(now, aT, aB, bpm)현재 beat 위치 = aB + (now − aT) × bpm/60. UI(플레이헤드)가 매 프레임 호출transportMath.ts:9-16
ctxTimeAtBeat(beat, aT, aB, bpm)역함수: beat → ctx 시간. 스케줄러(메트로놈, 이후 클립 재생)가 "이 beat를 언제 소리 내야 하나"에 사용transportMath.ts:19-26
clampBpm(bpm)20~300으로 clamp, 비유한값은 120(기본값)으로transportMath.ts:4-6, 28-31
✅ 이 설계의 이점 ① 매 프레임 갱신할 상태가 없다 — 파생값 계산만 있다. ② beat 단위 위치라 BPM이 바뀌어도 클립의 음악적 위치가 불변이다(타임라인도 beat 기준 project.ts:65). ③ 순수 함수라 오디오 없이 수학만 단위 테스트할 수 있다.

BPM 변경 = 재기준화 (re-anchoring)

재생 중 setBpm이 호출되면: 변경 시각의 위치를 구 bpm으로 확정해서 그 지점을 새 anchor로 삼고, 이후 계산부터 새 bpm 기울기를 쓴다. 위치는 연속이고 템포만 바뀐다. transport.ts:50-59

// transport.ts:53-57 — 재기준화
const now = getAudioContext().currentTime;
anchorBeats = positionBeatsAt(now, anchorCtxTime, anchorBeats, bpm); // 구 bpm으로 위치 확정
anchorCtxTime = now;
bpm = clamped;                                                        // 이후는 새 기울기

메트로놈은 살아 있는 anchor를 읽는 beatToCtxTime 콜백을 쥐고 있으므로, 재기준화 이후의 클릭은 자동으로 새 템포를 따른다. metronome.ts:21-24 · transport.ts:17-19

play / stop 생명주기와 엣지 케이스

  • autoplay 정책: 브라우저(Chromium)는 사용자 제스처 없이 오디오를 못 켠다. play()는 ctx.resume()을 await하고, suspended 동안 currentTime이 멈춰 있으므로 anchor는 resume 이후 시각으로 잡는다. transport.ts:28-32
  • 재진입 가드: playPending 플래그로 resume 대기 중 중복 play를 차단. transport.ts:11, 23
  • pending 중 stop: 세대 카운터 playEpoch — resume을 기다리는 사이 stop()이 오면 epoch가 바뀌어 pending play가 무효화된다. transport.ts:12, 31, 43
  • play()의 반환값은 "실제로 시작됐는가" — store는 true일 때만 isPlaying을 올린다. resume 실패 시 UI가 거짓 재생 상태로 가지 않는다. transport.ts:21-22 · useTransportStore.ts:20-27
  • stop = 곡 처음으로 (stoppedBeats = 0). pause는 현재 범위 밖. transport.ts:46

메트로놈 — lookahead 스케줄링

"A Tale of Two Clocks" 패턴. setInterval은 스케줄할 시점만 정하고, 클릭의 정확한 타이밍은 AudioContext 클럭으로 예약한다. JS 타이머의 지터가 소리 타이밍에 영향을 주지 않는다. metronome.ts:1-4

상수값의미
TICK_INTERVAL_MS25ms스케줄 판단 주기 (소리 타이밍과 무관)
LOOKAHEAD_SEC0.1s예약 선행 구간 — tick보다 충분히 길어 스로틀링 내성
ACCENT_FREQ_HZ / CLICK_FREQ_HZ1000 / 760마디머리(beat % 4 == 0) 악센트 구분. 4/4 고정은 TODO metronome.ts:14-15
CLICK_DURATION_SEC0.03s클릭당 1회용 OscillatorNode + 지수 감쇠 envelope metronome.ts:54-65
무할당 원칙과의 관계 클릭당 OscillatorNode 생성은 Web Audio의 1회용 노드 모델 그대로다. 무할당 원칙(Gotchas)은 rAF 등 고빈도 루프 대상이며, 이 tick은 25ms 간격·클릭당 1회라 대상이 아니다. 반면 rAF 경로인 getPositionBeats()는 숫자만 반환하고 할당이 없다. metronome.ts:3-4 · transport.ts:61-65 stop 시에는 bus GainNode를 disconnect해 이미 예약된 미래 클릭까지 함께 끊는다. metronome.ts:47-51

플레이헤드 — 고빈도 갱신의 store 우회

재생 위치는 초당 60회 갱신된다. 이걸 zustand에 넣으면 구독 컴포넌트 전체가 60fps로 리렌더된다. 대신 엔진에서 rAF로 직접 읽어 DOM transform만 갱신한다 — 재생 중에도 React 리렌더가 0회다. Playhead.tsx:6-7

  el.style.transform = `translateX(${beatsToPx(getPositionBeats())}px)`;
  rafId = requestAnimationFrame(tick);

job 상태 머신

취소 의미론 — "생성은 항상 취소 가능해야 한다"

수십 초짜리 생성 중에도 사용자는 작업을 계속할 수 있어야 한다는 것이 AI DAW의 전제다. 취소는 두 갈래로 구현돼 있다. jobs.py:69-75

  • task.cancel() — mock의 주 취소 경로. asyncio.sleep을 즉시 끊는다.
  • cancelled_flag (asyncio.Event) — 협조적 플래그. 실모델이 executor 스레드에서 돌 때를 대비한 계약. mock도 beat 경계마다 체크포인트를 두어 동일한 취소 의미론을 갖는다. music_generator.py:42-44
  • WS 단절 ≠ 취소. 취소는 오직 POST /jobs/{id}/cancel. 연결이 끊겨도 생성은 계속되고, 재접속하면 GET /jobs/{id} 스냅샷으로 복구한다. routes.py:100-101 · schemas.py:147
  • 멱등 — 이미 종료된 job의 취소는 already_finished no-op. jobs.py:70-71
WS 유실 창 없음 구독 등록 → 첫 스냅샷 송신 준비 사이에 await가 없다(asyncio는 await 지점에서만 선점). 등록 이후의 종료 이벤트는 큐로, 이전 종료는 스냅샷으로 반드시 전달된다. routes.py:77-91

mock 생성기 — 계약을 먼저 굳히는 장치

실제 AI 모델 없이 생성 계약 전체(요청→진행률→결과→취소)가 end-to-end로 동작하도록, stdlib만으로 만든 mock이 들어 있다. 실모델(MusicGen 계열, 라이선스 확인 후)로 교체돼도 generate() 시그니처는 유지된다. music_generator.py:1-6

  • 오디오 mock: 컨텍스트의 키(tonic)를 옥타브 2 주파수로, BPM을 beat당 펄스 길이로 반영한 지수 감쇠 톤 WAV — bpm이 귀로 확인된다. beat당 0.25s 지연으로 진행률 스트리밍을 시뮬레이션. music_generator.py:36-52
  • 진행 단계: loading_model(0.0) → generating(0.1~0.9) → encoding(0.95). music_generator.py:33, 51, 54
  • lengthBeats에 계약상 상한이 없어 mock 폭주 방지용 MAX_MOCK_BEATS = 64 clamp. generation/common.py:15-16
  • 실패는 계약의 failed 경로로 정규화된다 (GENERATION_FAILED + 메시지). jobs.py:118-121
⚠ 알려진 한계 (코드 주석에 명시) _jobs 딕셔너리와 staging/ 파일은 무한 누적된다 — 정리 정책은 계약 TODO. jobs.py:4
